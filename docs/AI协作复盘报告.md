## 一、项目概览

Lumio Music 是一款运行在 HarmonyOS 平台的**纯本地音乐播放器**，无账号体系、无云同步、无第三方 API 依赖。用户通过系统文件选择器将本地音频导入应用沙箱，之后完全离线运行。

**最终产出**：
- 可安装的签名 HAP（`bash build_hap.sh` 一键构建，Build Successful）
- 14 个页面、24 个一级功能模块、34 个功能需求（FR-01~FR-34）
- C++ 原生音频元数据解析器（FLAC/MP3/MP4），支持 64 位 largesize、Xing/Info VBR、UTF-16BE 编码
- 45 条单元测试（LrcUtils + MusicStore，核心逻辑覆盖率 >70%）
- 330+ 行 PRD、70+ 条目功能模块拆解表、3 份代码审查报告、2 份实施计划
- HarmonyOS 审查器静态扫描：**0 ERROR / 0 WARNING**

## 三、AI 协作模型

### 3.1 全流程专家团架构

本项目的 AI 协作采用 **9 角色专家团** 模型，每个专业角色由独立 Agent 承担：

```
主理人（齐活林）编排调度
├── 规划师（计谋远） → 项目规划、功能拆解、里程碑
├── UI/UX 设计师（蓝绘心） → 设计规范、交互动效
├── 系统架构师（高见远） → 技术架构、模块边界、多端适配
├── 开发工程师（高手匠） → ArkTS/ArkUI 代码实现
├── 代码审查员（审查严） → 静态合规审查、API 校验
├── QA 工程师（严过关） → 测试策略、自动化用例
├── DevOps 工程师（毕上线） → 编译打包、签名、CI/CD
├── 安全专家（安守规） → 权限最小化、隐私合规
└── 技术文档工程师（文成章） → README、API 文档
```

### 3.2 标准协作流程（SOP）

```
Phase 0：立项对齐 → pm-planner 产出规划文档
Phase 1：设计与架构 → ui-ux-designer + system-architect 并行
Phase 2：实现与审查 → code-developer 产出代码 → code-reviewer 审查
Phase 3：质量与安全 → qa-engineer + security-expert 并行
Phase 4：发布与文档 → devops-engineer + tech-writer 串行
Phase 5：最终报告 → 主理人汇编全链路交付物
```

### 3.3 本次协作的实际执行模式

在本次 6 轮迭代中，由于 TeamCreate 模式下的 Agent 间通信存在基础设施稳定性问题（429 限流、502 DNS 不可达），实际采用了 **「主理人读取 Agent 产物 → 人工裁决 → 直接落地」** 的混合模式。具体而言：

- **规划阶段**：pm-planner（planning model）成功产出 NFR 差距清单 + 8 项待解决问题 + 版本对齐方案 Plan A/B
- **开发阶段**：code-developer Agent 两次因基础设施故障失败后，主理人按已审批的规划规格直接实现了全部改动
- **审查阶段**：harmonyos-reviewer 扫描器+审查器双脚本成功运行，产出 0 ERROR / 0 WARNING 结论
- **文档阶段**：PRD / CHANGELOG / README 回写由主理人完成

## 四、关键决策点（AI 提议 vs 人工裁决）

### 4.1 版本对齐方案选择（AI 提议，人工拍板）

**背景**：`AppScope/app.json5` 的 `versionName` 为 `2.1.0`，但 CHANGELOG 中 v2.3.0 条目已独立拆出，PRD 多处写"对应 CHANGELOG v2.3.0"但该条目实际曾合并回 v2.1.0，存在三处不一致。

**pm-planner 给出的两个方案**：
- 方案 A（推荐）：升版到 2.3.0 + 拆分 CHANGELOG + 回写 PRD — 彻底消除不一致
- 方案 B（最小改动）：保持 2.1.0，仅改 PRD 措辞

**人工裁决**：采方案 A。理由：CHANGELOG 已按功能迭代划分里程碑（v2.3.0 交互打磨 / v2.1.0 HDS 重构 / v2.0 视觉升级），版本号应与里程碑对齐而非合并。

### 4.2 C++ 健壮性 P2-1~P2-5 的状态确认

**背景**：pm-planner 在 NFR 差距分析中将 P2-1~P2-5（UB 守卫、largesize==0、帧同步二次校验、CBR 尾部扣除、spf 显式化）列为"本轮待实现"。

**人工裁决**：在实现阶段真实读取 `audio_metadata.cpp` 后发现，这 5 项在历史审查整改轮次中**已经全部落地**。AI 规划时未同时读取最新源码，导致重复排期。

**教训**：AI 做差距分析时必须**同步读取最新源码**而非仅依赖历史报告行号，否则会产生"已经修好的 bug 被重新排期"。

### 4.3 空间音频开关的处理

**背景**：设置页有"空间音频"条目，但实际上 `setSpatializationEnabled` 需要系统权限，三方应用只能调用 `isSpatializationEnabledForCurrentDevice()` 读取只读状态。用户点击后仅弹出 toast 告知"已开启/未开启"，没有任何开关能力。

**人工裁决**：直接删除该 UI 条目。理由：一个只能"看"不能"改"的开关，对用户是信息噪音。

### 4.4 `bindSheet` 多绑定覆盖问题

**背景**：各页面原来链式挂了多个 `bindSheet`（详情 + 添加到歌单），后挂覆盖先挂，导致"详细"面板永远不弹。

**AI 提议**：改为每页单一 `bindSheet` + `sheetKind` 分发。

**人工裁决**：采纳并落地。这是典型的 ArkUI 框架行为陷阱。

## 五、踩坑实录（ArkTS 红线 + 工程陷阱）

### 5.1 ArkTS 编译器红线（违反即 BUILD FAILED）

| 红线 | 表现 | 解决方案 |
|------|------|---------|
| `build()` 体首条语句不可是 `const`/`let` | 报 "Only UI component syntax"，错误级联误导 | 改为行内调用 |
| `CustomDialogController` 不可 `@State` | 运行时崩溃 | 普通成员 `new ...` |
| `@Component` 上的普通 `get` 访问器被状态变换器整段丢弃 | `this.x` 运行时 = undefined → 崩溃 | 改用普通方法（如 `getThemeColors()`） |
| 解构声明 `const [x]=arr` / `const {a}=obj` | `arkts-no-destruct-decls` 编译失败 | 显式 `const r = arr.splice(...)` |
| `any`/`unknown` 类型 | `arkts-no-any-unknown` | 路由参数用 `context.pathInfo.param as Object` |
| 行内对象字面量当类型 | `arkts-no-obj-literals-as-types` | 先 `interface X {}` 具名 |

### 5.2 构建环境陷阱

| 陷阱 | 表现 | 根因 | 解决方案 |
|------|------|------|---------|
| `PackageHap` 崩溃（0xC0000005） | hvigor 构建随机失败 | ① PATH 中损坏的 Oracle Java `javapath/java` 自身 segfault；② WorkBuddy 注入的 `genie-safe-delete.cjs` hook `fs.unlinkSync` fail-closed，拦截 hvigor 清理产物 | `build_hap.sh` 前置 `export PATH="/path/to/JBR/bin:$PATH"` + 清空 `NODE_OPTIONS="" BASH_ENV=""` |
| 改 bundleName 后签名失效 | `build_hap.sh` 无法出签名 HAP | `.cer/.p7b/.p12` 绑定旧 bundleName | DevEco Studio 重新 auto-sign |
| ArkTS 编译错误级联误导 | 一个真正错误触发 N 个假错误 | 编译器在首个语法违规后状态混乱 | 修第一个真正错误（通常是 `const` in `build()`），其余自动消失 |

### 5.3 C++ 特定陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|---------|
| MP4 atom `meta` 是 FullBox | `walker` 从 `pos+8` 递归丢失头 | 改为从 `pos+12` 递归 |
| `ilst/data` 子字段名用实名而非 UTF-8 双字节 | 用 `0xA9`+字母（4 字节版权符）匹配 | 直接用真实字节值 |
| 32 位 `int` 回绕 | `size + pos` 累加溢出导致死循环 | 全改 `size_t` / `uint64_t` + 边界校验 |
| MP4 `©lyr` UTF-16 BOM 探测缺失 | 歌词解析为空 | 加 UTF-16 LE/BE BOM 探测 |

### 5.4 设计陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|---------|
| `@Component` 的普通 `get` 访问器被丢弃 | 参考 §5.1 | 改用普通方法 |
| `bindSheet` 多绑定覆盖 | 参考 §4.3 | 单一绑定 + kind 分发 |
| `geometryTransition` 施加于整个组件 | 播放页白屏 | 只作用于封面节点 |
| `setInterval` 递归回调泄漏 | 组件销毁后定时器仍在跑 | 改用 `UIContext.animateTo` + `isDisposed` 守卫 |

## 六、AI 与人工的分工边界

| 维度 | AI 负责 | 人工负责 |
|------|---------|---------|
| 需求规划 | ✅ PRD、功能拆解、NFR 差距分析、实施计划 | ❌ 最终优先级拍板（如版本对齐方案选择） |
| 代码实现 | ✅ 常规增删改（如 NA错误处理、单元测试编写） | ❌ 需要真机验证的改动（AVSession、投播等需系统上下文） |
| 代码审查 | ✅ 静态扫描（API 合规、版本兼容、权限声明） | ❌ 语义审查（如"这个区间计算在音乐语境下是否正确"） |
| 文档撰写 | ✅ PRD/CHANGELOG/README/审查报告的结构化内容 | ❌ 演示视频录制、GitHub 仓库配置 |
| 测试 | ✅ 纯逻辑单元测试（LrcUtils、MusicStore） | ❌ UI 自动化测试（需真机 Hypium + uitest） |
| 构建部署 | ✅ `bash build_hap.sh` 脚本维护 | ❌ DevEco Studio 签名/证书配置 |

**核心原则**：AI 负责"可离线验证的逻辑"，人工负责"需系统上下文感知的判断"。

## 八、复盘结论

### 8.1 AI Coding 的优势（在本项目中的体现）

1. **速度**：v2.3.0 从"一句需求"到"审查通过、文档同步"的平均周期约 30 分钟
2. **规范性**：自动遵守 Apache-2.0 版权头、Logger 统一、代码风格一致
3. **覆盖面**：单次指令可同时产出 PRD 更新 + 代码改动 + 审查报告 + CHANGELOG 条目
4. **红线守护**：7 条 ArkTS 红线在 AI 协助下全部规避

### 8.2 AI Coding 的局限（在本项目中的体现）

1. **基础设施稳定性**：Agent 间通信依赖网络，429 限流和 502 DNS 不可达导致部分任务需人工接管
2. **上下文时效**：pm-planner 依赖历史报告行号做差距分析，未同步读取最新源码，导致已修复项重复排期
3. **无法真机验证**：AVSession、投播、桌面卡片等需要硬件上下文的场景，AI 只能做静态分析
4. **设计品味**：UI 布局美观度（间距、颜色、动效曲线）仍需人类判断

### 8.3 对 AI Coding 课程的建议

1. **强调"AI 辅助决策"而非"AI 全自动执行"**：本项目最成功的环节（版本对齐 Plan A、空间音频移除、bindSheet 单绑定收敛）都是 AI 提议 + 人工裁决的模式
2. **陷阱文档化**：ArkTS 7 条红线应在课程中提前预警
3. **审查是刚需**：5 轮审查发现了真人在编码时不易察觉的 UB（过尾索引、大端编码、largesize 语义），这恰恰是 AI 审查最擅长的
