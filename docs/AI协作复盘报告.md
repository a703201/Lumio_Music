## 一、项目概览

Lumio Music 是一款运行在 HarmonyOS 平台的**纯本地音乐播放器**，无账号体系、无云同步、无第三方 API 依赖。用户通过系统文件选择器将本地音频导入应用沙箱，之后完全离线运行。

**最终产出**：
- 可安装的签名 HAP（`bash build_hap.sh` 一键构建，Build Successful）
- 14 个页面、24 个一级功能模块、34 个功能需求（FR-01~FR-34）
- C++ 原生音频元数据解析器（FLAC/MP3/MP4），支持 64 位 largesize、Xing/Info VBR、UTF-16BE 编码
- 45 条单元测试（LrcUtils + MusicStore，核心逻辑覆盖率 >70%）
- HarmonyOS 审查器静态扫描：**0 ERROR / 0 WARNING**

## 三、AI 协作模型

本项目采用 **「主理人 + 9 角色专家团」** 模型：

- **规划师**（pm-planner）→ 项目规划、功能拆解、里程碑
- **开发工程师**（code-developer）→ ArkTS/ArkUI 代码实现
- **代码审查员**（code-reviewer）→ 静态合规审查、API 校验
- **QA 工程师** → 测试策略、自动化用例
- **DevOps 工程师** → 编译打包、签名
- **安全专家** → 权限最小化、隐私合规
- **技术文档工程师** → README、API 文档

**核心原则**：AI 负责"可离线验证的逻辑"，人工负责"需系统上下文感知的判断"。

## 四、关键决策点

1. **版本对齐方案选择**：Plan A（升版到 2.3.0 + 拆分 CHANGELOG）vs Plan B（保持 2.1.0）→ 采 A
2. **空间音频开关移除**：只能"看"不能"改"的开关是信息噪音 → 直接删除
3. **`bindSheet` 多绑定收敛**：单一绑定 + `sheetKind` 分发
4. **C++ 健壮性状态确认**：AI 规划时重复排期已修复项，需同步读取最新源码

## 五、踩坑实录

### ArkTS 编译器红线
- `build()` 体首条不可是 `const`/`let`
- `@Component` 上的 `get` 访问器被状态变换器丢弃
- 解构声明 `const [x]=arr` / `const {a}=obj` 禁止
- `any`/`unknown` 类型禁止

### 构建环境陷阱
- PATH 中损坏的 Oracle Java 自身 segfault
- `genie-safe-delete.cjs` 拦截 hvigor 清理产物
- 改 bundleName 后签名失效

### C++ 特定陷阱
- MP4 atom `meta` 是 FullBox，需从 `pos+12` 递归
- 32 位 `int` 回绕导致死循环
- `©lyr` UTF-16 BOM 探测缺失
- NAPI `new taskpool.Task(()=>{})` 在真机静默抛 10200014

## 八、复盘结论

**AI Coding 优势**：速度快（单轮 ~30 分钟）、规范性强（统一版权头/Logger/风格）、覆盖面广（一次产出代码+审查+文档）

**AI Coding 局限**：基础设施不稳定（429/502）、上下文时效差（需同步读最新源码）、无法真机验证、设计品味需人类判断

**核心心得**：AI 不是替代开发者，而是让开发者把精力从"怎么写"转移到"做什么"和"为什么这样做"。
