## 二、P0 清单（阻断出包）

### P0-1　`ListItem.onDragStart` 返回 void，违反官方签名 → 编译不通过

**文件**：`entry/src/main/ets/pages/PlaylistDetail.ets:474-476`

```ets
.onDragStart(() => {
  this.dragFrom = index;      // ← 无返回值
})
```

**问题**：官方签名要求返回背板图描述，**不接受 `void`**：

> `onDragStart(event: (event: DragEvent, extraParams?: string) => CustomBuilder | DragItemInfo): T`
> —— 《通用事件 · 拖拽事件》，返回值类型 `CustomBuilder | DragItemInfo`

TypeScript 赋值兼容性中，源函数返回 `void` **不可**赋给要求 `CustomBuilder | DragItemInfo` 的目标类型，DevEco 编译期报 `TS2322: Type 'void' is not assignable to type 'CustomBuilder | DragItemInfo'`。

### P0-2　ListItem 未设 `draggable(true)` → 拖拽永不发起，功能 100% 不可用

**文件**：`entry/src/main/ets/pages/PlaylistDetail.ets:471-477`（配套 `:442` 的「长按歌曲可拖动排序」提示）

**问题**：官方明确 ArkUI 仅对 **Search、TextInput、TextArea、RichEditor、Text、Image、Hyperlink** 提供默认拖出能力（其 `draggable` 默认 `true`）：

> 其他组件需要将 `draggable` 属性设置为 true，并在 `onDragStart` 等接口中实现数据传输相关内容，才能正确处理拖拽。

本页 `ListItem` 内是 `Row`/`Image`/`Text` 组合容器，`ListItem` 自身 **不在默认可拖出清单**，且未设 `.draggable(true)`、未在 `onDragStart` 中 `setData`/返回背板图 → 长按 500ms 后**不会进入拖拽态**，`onDragStart`/`onDrop` 均不触发。UI 提示语与实际能力不符，属功能性欺骗。

### P0-1 + P0-2 统一修复建议（推荐方案 A）

改用官方推荐的 **`ForEach.onMove`**（API 12+，API 24 完全可用）。框架自带长按拖拽识别、跟手动画、落位动效与自动重排，无需 `draggable`/`onDragStart`/`onDrop` 手工拼装：

```ets
List() {
  ForEach(this.songs, (song: SongItem, index: number) => {
    ListItem() {
      this.buildSongItem(song, index)
    }
  }, (song: SongItem): string => `${song.id}`)
    .onMove((from: number, to: number): void => {
      // from/to 由框架给出，语义即「把 from 位置的项移动到 to 位置」
      this.store.reorderPlaylistSongs(this.playlistId, from, to);
      this.reload();
    })
}
.width('100%')
.layoutWeight(1)
.scrollBar(BarState.Off)
.padding({ bottom: this.bottomHeight + 16 })
// 注意：ForEach 必须是 List 的直接子节点；key 必须稳定（当前 `${song.id}` 已满足）
```

采用方案 A 后，可**一并删除** `@State dragFrom`（P2-6）、`handleDrop()`（P1-1/P2-7）、`List.onDrop`（P2-11），代码净减约 25 行。

### P0-3　MP4 64-bit largesize：`pos + size64` uint64 加法回绕 → 死循环 / ANR

**文件**：`entry/src/main/cpp/audio_metadata.cpp:366`（新增 largesize 路径引入）

```cpp
if (static_cast<uint64_t>(pos) + size64 > buf.size()) {   // ← 回绕点
    break;
}
...
pos += static_cast<size_t>(size64);                        // :452
```

**问题**：`size64` 由文件中任意 8 字节构造，取值域为完整 `[0, 2^64-1]`。当 `size64 ≥ 2^64 - pos` 时，`pos + size64` 按模 2^64 **回绕成一个极小值**，`> buf.size()` 判定 **通过**；随后 `pos += size64` 使 `pos` 同样回绕变小，外层 `while` 从更靠前的位置重新开始 → **无限循环，主/工作线程挂死（ANR）**。

- 32-bit 路径不受影响：`size64 ≤ 0xFFFFFFFF`，与 `pos` 相加不可能回绕，这是本轮**新引入**的缺陷。
- 用户关注的 `pos + 16 > end`（:349）与 `size64 < headerLen`（:362）两处**均已正确覆盖**，遗漏的正是这第三处。

**修复**（改加法为减法比较，`pos + 8 <= buf.size()` 已由 :342 循环条件保证 `buf.size() - pos` 不下溢）：

```cpp
// P0：用减法比较，杜绝 uint64 加法回绕（largesize 可为任意 64 位值）
if (size64 > static_cast<uint64_t>(buf.size() - pos)) {
    break;
}
```

> 附加建议：`pos += static_cast<size_t>(size64)` 在 32 位 ABI（armeabi-v7a）下 `size_t` 为 32 位会截断。当前 `deviceTypes` 仅 `phone`（arm64-v8a）不受影响，但建议加 `static_assert(sizeof(size_t) >= 8, "64-bit size_t required");` 固化前提。

### P1-1　`dragIndex` 字段不存在于 extraParams（死代码 + 字段名误导）

**文件**：`PlaylistDetail.ets:150-155`

**官方 extraParams 仅定义两个字段**（《通用事件 · 拖拽事件 · extraParams说明》）：

|---|---|---|
| `selectedIndex` | number | **仅在 ListItem 组件的拖拽事件中生效**，否则返回 undefined |

const parsed = JSON.parse(extraParams) as Record<string, number>;
if (typeof parsed['insertIndex'] === 'number') {

### P1-2　MP3 sideInfo 的 layer 判定与注释颠倒 → MPEG2/2.5 单声道 VBR 时长错误

**文件**：`audio_metadata.cpp:292-299`

代码 `:268` 自己定义了 `layer` 位值语义：`3=LayerI, 2=LayerII, 1=LayerIII`，但 `:293` 写成：

```cpp
if (layer == 3) {        // 注释写「Layer III」，实为 Layer I
    sideInfo = (ver == 3) ? ((chanMode == 3) ? 17 : 32) : ((chanMode == 3) ? 9 : 17);
} else if (layer == 2) { ...
} else {                 // 注释写「Layer I」，真正的 Layer III(layer==1) 落到这里
    sideInfo = (ver == 3) ? ((chanMode == 3) ? 17 : 32) : 17;
}
```

**后果**：Xing/Info 头**只存在于 Layer III**。真正的 Layer III 走进最后一个 `else` 分支：
- MPEG1（ver==3）：得 17/32 —— 与规范巧合相同，故未暴露；
- **MPEG2 / MPEG2.5 单声道：得 17，规范值应为 9** → `xingOff` 偏移错 8 字节 → 匹配不到 "Xing"/"Info" → 退回 CBR 近似 → 低采样率 VBR MP3 时长明显偏差。

**修复**：

```cpp
// Xing/Info 仅存在于 Layer III（layer 位值 1）
int sideInfo = -1;
if (layer == 1) {
    sideInfo = (ver == 3) ? ((chanMode == 3) ? 17 : 32)    // MPEG1  : mono 17 / stereo 32
                          : ((chanMode == 3) ?  9 : 17);   // MPEG2/2.5: mono  9 / stereo 17
}
if (sideInfo >= 0) {
    size_t xingOff = i + 4 + static_cast<size_t>(sideInfo);
    if (xingOff + 12 <= buf.size() && (tagEq(&buf[xingOff], "Xing") || tagEq(&buf[xingOff], "Info"))) {
        ...
    }
}
```

> 边界方面：`xingOff + 12 <= buf.size()` 覆盖 flags(+4..+7) 与 frames(+8..+11) 的最大下标 `xingOff+11`，**边界检查正确无越界**；`frames * spf * 1000 / sr` 已用 `uint64_t` 提升，**无溢出**。这两点验证通过。

### P1-3　mvhd version==1 读取了 64 位 duration 的高 32 位 → 时长恒为 0

**文件**：`audio_metadata.cpp:395-398`

ISO/IEC 14496-12 中 mvhd v1 布局（相对 `p`）：`version+flags`(4) → `creation_time`(8) → `modification_time`(8) → `timescale`(4, p+20) → **`duration`(8, p+24..p+31)**。

代码读 `p+24..p+27`，即 64 位时长的**高 32 位**；正常时长（< 2^32）下该值恒为 0 → `dur == 0` → `parseMp4` 的 `if (ts > 0 && dur > 0)` 不成立 → v1 mvhd 的 M4A **时长解析失败**。`need = 32`（:376）字节数计算正确，故无越界，纯取值错误。

```cpp
} else {
    mvhdTs = (static_cast<uint32_t>(buf[p + 20]) << 24) | ... ;   // 不变
    // v1 的 duration 为 64 位，取低 32 位（p+28..p+31）；高位非 0 属超长媒体，按饱和处理
    uint32_t hi = (static_cast<uint32_t>(buf[p + 24]) << 24) | (static_cast<uint32_t>(buf[p + 25]) << 16) |
                  (static_cast<uint32_t>(buf[p + 26]) << 8)  |  static_cast<uint32_t>(buf[p + 27]);
    uint32_t lo = (static_cast<uint32_t>(buf[p + 28]) << 24) | (static_cast<uint32_t>(buf[p + 29]) << 16) |
                  (static_cast<uint32_t>(buf[p + 30]) << 8)  |  static_cast<uint32_t>(buf[p + 31]);
    mvhdDur = (hi != 0) ? 0xFFFFFFFFu : lo;
}
```

> 实测的 `lose_my_mind.m4a` 时长正确（209051ms），说明该样本为 v0 mvhd —— **v1 分支未被真实验证覆盖**，需补样本（见复验清单第 7 项）。

### P1-5　递归 `animateTo` 无销毁/隐藏守卫 → 组件销毁后回调仍在跑 + `isBreathing` 卡死

**文件**：`Playlists.ets:54-55`（空 `aboutToDisappear`）、`:61-81`（`startBreathing`）

两个缺陷：

1. **销毁后泄漏**：`onFinish` 闭包持有 `this` 并无条件递归。页面 pop 销毁后，在途动画的 `onFinish` 仍会触发 → 继续 `this.getUIContext()`（已销毁组件上下文，可能抛异常）并写 `this.emptyIconScale` → 动画链**永不终止**。`aboutToDisappear()` 为空，未做任何清理。
2. **`isBreathing` 卡死**：页面被 `onHidden`（跳详情页）时动画可能被中断而 **`onFinish` 不触发**，`isBreathing` 永久停在 `true`；返回页面后 `reload()` → `startBreathing()` 被 `:67` 的守卫直接挡回 → **呼吸动画再也不恢复**。

```ets
private isBreathing: boolean = false;
private isDisposed: boolean = false;
private pageVisible: boolean = true;

aboutToDisappear(): void {
  this.isDisposed = true;      // 断开递归链
  this.isBreathing = false;
}

private startBreathing(): void {
  if (this.isDisposed || !this.pageVisible || this.playlists.length !== 0) {
    this.emptyIconScale = 1.0;
    this.isBreathing = false;
    return;
  }
  if (this.isBreathing) {
    return;
  }
  this.isBreathing = true;
  this.getUIContext().animateTo({
    duration: 1000,
    curve: Curve.EaseInOut,
    onFinish: () => {
      this.isBreathing = false;
      this.startBreathing();   // 守卫在函数入口统一判定
    }
  }, () => {
    this.emptyIconScale = this.emptyIconScale === 1.0 ? 1.08 : 1.0;
  });
}
```

配合 `NavDestination` 生命周期（`:393-399`）：

```ets
.onShown(() => {
  this.pageVisible = true;
  this.reload();               // reload 内部会在空列表时重启呼吸
})
.onHidden(() => {
  this.pageVisible = false;
  this.isBreathing = false;    // 允许 onShown 后重新起链，避免标志卡死
})
```

### P1-6　【关联/存量】`taskpool.Task` 传入闭包而非 `@Concurrent` 顶层函数 → C++ 解析路径在真机上从不执行

**文件**：`entry/src/main/ets/utils/AudioMeta.ets:41-45`（非本轮改动，但**决定本轮 C++ 成果能否生效**）

```ets
const task: taskpool.Task = new taskpool.Task(() => {
  return NativeUtils.getInstance().parseAudioMetadata(src);   // ← 箭头闭包
});
const native = await taskpool.execute(task) as AudioMeta;
```

ArkTS taskpool 强制要求并发函数**使用 `@Concurrent` 装饰**且**定义在文件顶层**，否则抛 `10200014 The function is not marked as concurrent`。全工程 `grep -rn "@Concurrent" entry/src/main/ets/` **零命中**。

**后果**：该调用必然抛异常 → 被 `:50` 的 `catch` 静默吞掉（仅 `Logger.debug`）→ **永远返回 MediaKit 的结果**，本轮新增的 VBR 时长估算与 64-bit largesize **在真机上根本不会被执行**。这也解释了为何 g++ standalone harness 一切正常而端侧无从感知。

```ets
// 顶层定义（与 class 平级）
@Concurrent
function parseMetaOnWorker(src: string): AudioMeta | undefined {
  return NativeUtils.getInstance().parseAudioMetadata(src);
}

// 调用处
const native = await taskpool.execute(parseMetaOnWorker, src) as AudioMeta;
```

> 注意：每个 taskpool worker 拥有独立 VM，`NativeUtils` 单例需在 worker 侧可重新 `import` 并完成 `.so` 加载；`@Concurrent` 函数内只能使用入参与顶层导入，不可捕获外层变量。此项必须真机验证（复验清单第 6 项）。

### P1-7　ID3v2 `enc == 2`（UTF-16BE 无 BOM）被按小端解码 → 中文乱码

**文件**：`audio_metadata.cpp:205-215`

ID3v2 编码字节语义：`0x01` = UTF-16 **带 BOM**；`0x02` = **UTF-16BE 无 BOM**。代码把两者同路处理，且在无 BOM 时 `isBE` 初值为 `false`（小端）→ `enc == 2` 的帧字节序判定必然反向 → 中文标题/艺术家乱码。

```cpp
bool isBE = (enc == 2);   // 0x02 = UTF-16BE without BOM，缺省即大端
unsigned int s = txtOff;
if (txtLen >= 2 && buf[s] == 0xFF && buf[s + 1] == 0xFE) {
    s += 2; isBE = false;
} else if (txtLen >= 2 && buf[s] == 0xFE && buf[s + 1] == 0xFF) {
    s += 2; isBE = true;
}
```

| P2-4 | `:320-325` | CBR 兜底未扣除尾部 ID3v1(128B)/APE tag，时长略偏大；首帧码率对真 VBR 无代表性 | 检测尾部 `TAG`/`APETAGEX` 并从 `audioBytes` 扣除 |
| P2-5 | `:256-263` | 帧同步未做"下一帧头校验"（按 frameLen 跳转后再验 `0xFF Ex`），易被随机字节误同步 | 命中候选后按帧长跳转校验第二帧，连续 2 帧一致才采信 |
