## 修复已知遗留 + 权限引导 + 空态完善（P0 收尾）

### 1. 修复引擎队列在导入/删除歌曲后不同步（已知遗留）
- 根因：`AudioRendererController.songList` 仅在构造时读一次 AppStorage('songList')，导入/删除歌曲后引擎队列不更新 → 已删歌曲仍留在队列，`playNext` 可能跳到已删文件。
- 新增 `AudioRendererController.reconcileWithLibrary(library: SongItem[])`：差量合并（移除曲库中已删项并修正 musicIndex + 把新导入歌曲追加队尾），并 `syncQueue()` 回写 AppStorage + AVSession；当前曲被删时续播相邻或停止。
- 调用点：`LocalLibrary.onPickMusic`（导入后）、`LocalLibrary.deleteSong`、`ManageSongs.doDelete`。
- 设计取舍：仅在实际导入/删除时调用，**不在进入播放页时调用**，以免覆盖用户在队列弹窗里的手动"移除/下一首播放"。副作用：手动移除的歌若在之后导入/删除时被重新并入队列尾部（可接受）。

## 点歌即播体验优化

### 目标
原先「库/收藏/历史/搜索」列表点行只跳转播放页、不自动播放（需再按播放键）；而队列弹窗点行已自动播放（行为不一致）。统一为"点歌即播"。

### 实现
- `AudioRendererController` 新增 `playFromList(list, index)`：语义化封装 `setQueue(list, index, true)`（设队列 + 索引 + syncQueue + 起播）。无新 API/权限。
- 改造 4 个歌曲列表页点击处理：
  - `LocalLibrary.playSong`（song）
  - `Favorites.ets` 行 onClick
  - `PlayHistory.ets` 行 onClick
  - `Find.ets`（搜索结果）行 onClick
  - 均改为 `AudioRendererController.getInstance().playFromList(this.store.songs, index)` 后 `pushPathByName('PlayerPage')`；`Favorites/PlayHistory/Find` 补 `import { AudioRendererController }`。
  - 移除各页原 `AppStorage.setOrCreate('selectIndex'/'songList')` 手工写法（改由引擎 syncQueue 统一回写）。
- 刻意**不改**：`Layout.openPlayer()`（迷你播放条→打开当前播放页，属"打开"非"点歌"，重播不合适）；`PlayerPage.aboutToAppear` 仍把 songList 重置为 store.songs（与引擎队列一致，无错位）。

### 设计取舍 / 边界
- 队列统一用 `store.songs`（全库），与改动前各页行为一致（收藏/历史点歌也是在全库顺序里播放）→ 零索引错位风险，最低回归面。
- 未做"按上下文列表（收藏/历史）作为队列"的增强（会改变队列语义、与 reconcileWithLibrary 交互更复杂）——留作可选后续。
- 索引一致性：playFromList 经 setQueue→play→updateMusicIndex 同步 selectIndex + AVSession metadata，锁屏/通知标题即时更新；isFirst 置 false，播放键逻辑正确。

### 验证限制（同前）
- 沙箱无法出 HAP，需 DevEco 真机/模拟器验证：4 个列表点歌是否进入即播、锁屏标题正确、当前播放高亮一致。

## 封面改造后 CompileArkTS 再报 4 错（3 error + 1 warn）定点修复

`assembleHap` 在封面改动后报错，全部集中在封面相关两文件：

1. **CoverCache.ets:58** `preload(songs: { src: string }[])` 内联对象字面量作类型 → `arkts-no-obj-literals-as-types`。
   → 改为顶层 `interface CoverSource { src: string }`，参数用 `preload(songs: CoverSource[], ...)`。调用点传 `SongItem[]`（`SongItem` 含 `src: string`）结构兼容，无需引入 SongItem 造成循环依赖。
2. **PlayerInfoComponent.ets:297-298** `isPixelMap(): value is PixelMap` 用 `is` 类型谓词（`arkts-no-is`）+ `'getImageInfo' in value` 的 `in` 运算符（`arkts-no-in`），ArkTS 均不支持。
   → 删除 `isPixelMap`，改用 `songLabel instanceof image.PixelMap`（`image` from `@kit.ImageKit`，PixelMap 是类，instanceof 合法且可做类型收窄）。Resource 分支仍是 `songLabel as Resource`。
3. **PlayerInfoComponent.ets:267（WARN）** `getMediaContent` 可能抛异常未捕获 → “Function may throw exceptions”。
   → 用 `try/catch` 包裹 `getMediaContent` 调用；为防 ArkTS 确定性赋值告警，`sourcePromise` 给初始值 `Promise.reject(new Error('unreachable'))`。

### ArkTS 可复用红线（沉淀）
- 禁止：内联对象字面量当类型（`{a:string}[]`）→ 用 `interface`；`x is T` 类型谓词；`in` 运算符判属性。
- 调 `throws` 声明 API（如 `resourceManager.getMediaContent`）必须 try/catch 或上层 throws；且 `let` 变量需保证所有路径确定性赋值。
- **⚠️ PixelMap 没有可访问的运行时构造器**：`PixelMap` 只能经 `image.createImageSource(...).createPixelMap()` 工厂创建，故 `instanceof image.PixelMap`（或 `instanceof PixelMap`）在 API 24 **编译失败**——`image.PixelMap` 只是类型、不是 `image` 命名空间上的运行时值（报错 `Property 'PixelMap' does not exist on type 'typeof image'`）。`music.ets` 用 `image.PixelMap` 作类型注解能编译，正是因为它是类型而非值。
- 运行时区分 `Resource | PixelMap` 联合类型 → 用**鸭子类型**而非 `instanceof`/`is`/`in`（三者 ArkTS 均禁）：`private isPixelMap(v: Resource | PixelMap): boolean { return typeof (v as PixelMap).getImageInfo === 'function'; }`。`PixelMap` 有 `getImageInfo` 方法、`Resource`（`$r()` 产物，仅 `id/type/params`）没有 → 稳定区分。函数返回 `boolean`（非谓词），调用处用 `v as PixelMap` / `v as Resource` 显式收窄。
- 改动文件：`CoverCache.ets`、`PlayerInfoComponent.ets`。
